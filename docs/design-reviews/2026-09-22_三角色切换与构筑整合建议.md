# 游戏设计评审：三角色切换与构筑整合建议

## 0. 决策摘要

**[提案] 推荐方向：三名角色共同完成一套局内构筑；每名角色在一轮战斗中承担可理解的任务；常规攻击维持战斗，玩家重点决定关键技能和交接时机。**

- 玩家报告的问题：技能之间多为并列输出；每次升级比较负担大；技能越多，指定成长越难抽到；三角色切换与多技能手动操作难以兼顾。
- 本次需要讨论：一局的构筑单位、主动操作负担、离场效果规则、基础成长与机制选择的分工。
- 当前状态：设计草案，未批准任何玩法改动。仅新增本文，不修改技能、奖励、画面或存档。
- 本次分析完成条件：六款参照游戏各自的解法有来源；本项目事实有源码依据；建议与现状分开；给出可证伪的小规模验证方案。
- 玩法方案的完成条件另见第 13 节，不能用完成本文代替游戏验证。

## 1. 范围与约束

- 目标玩家：希望逐局学习搭配的幸存者玩家，兼顾熟练切人操作；具体目标操作强度待试玩确定。
- 目标场景：从前期清怪到最终 Boss 的整局体验。
- 范围内：队伍分工、技能交接、输入负担、构筑选择、发牌方向和反馈。
- 不在本次执行范围：实际重构、数值平衡修改、恢复旧天赋、发布和 GitHub 提交。
- 核心承诺：三角色互切；角色能在不同构筑中担任主要输出；切换具有战术意义。
- 反目标：一名角色长期独占操作、其余角色只能提供固定增益；机械式按固定顺序切人；为了有深度而持续增加按键和资源条。
- 生产约束：单人开发，先以现有技能做一个原型。保留既有攻击、画面与性能要求；新增机制的性能成本必须单独测量。
- 存档约束：任何后续试验应独立于正式存档，不在本草案中默认授权迁移。

## 3. 玩家问题与成功标准

**[推断] 根因是三个需求同时争夺注意力：密集敌人下的走位、三人技能与切换时机、三套独立成长候选的比较。手动开关解决释放权限，不能单独解决分工和阅读负担。**

期望玩家能回答：

1. 这局靠哪种机制处理怪物和 Boss？
2. 三名角色分别在什么情况下上场，上场完成什么？
3. 上一轮失败缺少的是伤害、覆盖、控制、资源还是交接时间？
4. 下一次成长为什么能改善上述问题？

成功信号：玩家能说明搭配原因；三名角色都有可观察的贡献；少看技能栏也能完成普通战斗；失败后提出具体调整；定向成长不依赖某张稀有卡。

否定条件：只是更频繁按切换；只比较卡牌颜色/稀有度；同一固定顺序应对所有敌人；两名角色长期失去必要性；减少选项后成型率反而降低。

**[提案] 机制变化元素：**建立少量可跨角色使用的条件；改写成长候选范围；明确离场状态的保留/撤销；转移已有增益或资源必须写明成本；不恢复旧树。

核心机制卡（原型而非已定规则）：

- 名称：地面持续输出的三角色接力。
- 前置：法师、机械师、枪手在队；核心技能可获得，基础循环不依赖稀有强化。
- 动作：法师铺路；机械师部署减速区域；枪手削甲并处理优先目标。
- 权限/成本：沿用各技能解锁、冷却和切换条件，实际连续释放窗口需要测量。
- 状态变化：场上路径持续；力场限制敌人移动；护甲被降低；当前角色改变。
- 反馈：玩家能看见怪物留在路径内、护甲变化和关键技能就绪。
- 结束：按各自计时自然结束；铺路中切走停止新增路径，不能假装铺路继续。
- 失败/恢复：某技能未就绪时仍可走位普攻；通过替代控制或调整路线维持基础解法。

## 5. 链、环、网络与生态

**[提案] 一局以共同战斗机制组织队伍分工。**例如地面持续输出、集中破甲后的爆发、积累资源后的短时输出。它们是分析描述，暂不新增名为“流派”的 UI 系统。

动作链：观察敌人 → 当前角色完成任务 → 判断交接窗口 → 切人使用上一段留下的条件 → 观察缺口 → 选择能解决缺口的成长。

资源流：优先复用“时间/命中 → 现有角色资源 → 技能/入场效果 → 战场优势”，避免为切换额外建立第二套万能资源。

- 正反馈：可靠控制提高持续命中，持续命中改善输出与现有能量获取。
- 约束：站场时间竞争、技能冷却、消耗与保留之间的取舍；不能让任意触发递归生成自身。
- 恢复环：错过交接后仍可使用普通攻击与移动，避免整轮失效。
- 学习环：死亡/失误 → 看懂具体短板 → 换一项构筑或操作 → 验证。
- 生态：快速敌人提高控制价值；高护甲目标提高削甲价值；单体目标要求不完全依赖击杀和怪物密度。
- 跨角色配合不能全部写成“A 给 B 增伤”。可通过留场效果、空间控制、资源转化和完成条件产生联系。

## 6. 六款游戏对照与玩家体验

以下“玩法事实”来自 S1—S10；“启示”是本项目的设计推断，不代表原开发者的设计声明。

| 游戏 | 玩法事实与构筑位置 | 对本项目的启示 |
| --- | --- | --- |
| 原神 | 切换角色并组合元素、技能和队伍能力（S1） | 学习队员创造条件、接续使用条件；把局前队伍方向与战斗执行分开。其长期角色/装备培养不应直接搬成高频局内菜单 |
| 鸣潮 | 切换与变奏/延奏相连；一些延奏给后续角色明确收益（S2、S3） | 交接应有可理解的产物和时机；复杂取消、弹反和高频动作执行不宜全部叠加到密集弹幕生存压力 |
| 吸血鬼幸存者 | 自动攻击、局内武器升级、滚雪球式生存（S4、S5） | 常规火力可以自动维持，把注意力留给移动和成长；增加武器通常不应增加相同数量的必须手动动作 |
| 土豆兄弟 | 默认自动武器，可手动瞄准；武器数量有限；波次之间购物组合角色、属性与装备（S6） | 把战斗与阅读分时处理，用角色条件和有限投入制造取舍；不必照搬商店货币和停波节奏 |
| 哈迪斯一代 | 武器提供基本动作，祝福改变这些动作和组合；局内重复尝试不同组合（S7、S8） | 同一套熟悉操作可以容纳很多构筑；新增成长优先改变已有行为与条件 |
| 以撒的结合：重生/忏悔 | 随机动作射击；大量道具、主动道具、协同与武器组合（S9、S10） | 少量基础行为通过组合产生变化；随机适应本身也是玩法。它不保证每局得到预定完整配方，不适合作为本项目定向发牌的唯一参照 |

十二视角合并检查：

| 视角 | 本次结论 |
| --- | --- |
| 心智模型与可读性 | 优先说明上场任务、离场留下什么、下一段需要什么 |
| 能动性与决策质量 | 用控制/覆盖/资源等真实问题支撑选择，不只比较总伤害 |
| 操作、战术、战略 | 操作负责走位与释放，战术负责切人，成长负责决定这些行为的价值 |
| 风险与公平 | 允许失误恢复，避免缺一张卡整套失效 |
| 反制与反事实 | 不同敌人应改变成长优先级；替代控制和资源来源要存在 |
| 感官反馈 | 关键状态醒目，避免增加满屏技能提醒 |
| 节奏与张力 | 控制常规阅读频率，保留稀少高价值的大招时刻 |
| 注意力 | 暂以每角色一个主要手动决策技能作为原型目标，不是正式装备上限 |
| 构筑身份 | 玩家能描述整支队伍如何合作，分工可随局内成长变化 |
| 失败与学习 | 收集失败原因及下一局调整，不以通关率单独判断深度 |
| 动机与重玩 | 保证方向可推进，同时保留探索和替代路径 |
| 角色幻想 | 每个角色可在不同路线担任核心，避免永久固定主辅身份 |

## 7. 系统全景影响

| 系统 | 建议影响及保留条件 |
| --- | --- |
| 输入、普攻、主动技能、大招 | 保留自动/手动选择；降低必须精准管理的技能数；大招仍贵且强 |
| 移动、空间、敌人、Boss | 通过现有区域、牵引、敌人速度和护甲验证配合，不先增加敌方机制 |
| 三角色轮转 | 明确离场状态合同；短站场和长站场都可以有价值，不要求三等分时间 |
| 状态与资源 | 优先使用现有护甲、减速、临时血量、零件；不添加易伤乘区 |
| 构筑、祝福、装备、解锁 | 团队基础成长与关键机制选择分开；技能获得不必自动扩大所有常规候选 |
| 等级天赋 | 当前占位不得作为已实现配合；未来真正分支与普通升级合并呈现，避免连续弹窗 |
| HUD、菜单、教程、结算 | 显示关键技能准备和留下的条件；提供原因而非只显示 DPS |
| 波次、N 层、主线、营地、奖励货币 | 本次不修改；试验先固定相同难度、敌群和初始条件 |
| 音效、画面、镜头、性能、无障碍 | 复用现有效果；关键反馈不能只靠颜色；不通过减少既有技能或弹幕证明优化 |
| 存档、设置、成就、发布 | 文档阶段不改变；实现前需为新规则单列版本、兼容与回滚约束 |

## 8. 整局生命周期

| 阶段 | 原型目标与待验证点 |
| --- | --- |
| 进入前 | 知道队伍基本分工；不要求一次规划三套完整构筑 |
| 前 30 秒 | 三名角色具有可理解的基本贡献，避免核心协同完全等待随机解锁 |
| 0—3 分钟 | 确定一种输出机制和一个配合条件；具体成长节点待试验 |
| 3 分钟小 Boss | 验证基础循环面对少目标仍可工作 |
| 3—6 分钟 | 补足控制、范围、资源或生存短板 |
| 6 分钟强袭 | 验证切换决策与密集走位能否兼顾 |
| 6—9 分钟 | 保留替代强化和转向机会，避免固定配方 |
| 9 分钟小 Boss | 检查是否只有一名角色贡献、是否依赖怪群充资源 |
| 9—12 分钟 | 以稳定和完善为主，不强迫重新学习一套全新操作 |
| 最终 Boss | 基础配合对单体有效；控制收益不足时有替代解法 |
| 结算/死亡 | 玩家能说明失败原因和下一次调整 |
| 营地/重试 | 学到的规则可以迁移到不同卡牌和队伍，而非背诵固定顺序 |

上述时间节点沿用项目现有流程讨论，不是新增波次设计。

## 9. 退化模式与边界

- 一主两挂件：检查实际贡献、站场任务和每个角色可成为核心的路线；不以平均站场时间作为解决办法。
- 切人打卡：不给无条件切换持续叠增伤；需要完成有意义的任务或响应场面。
- 一套万能配方：同一短板提供多种解法；探索选项不全部锁在已选标签。
- 随机卡门禁：基本协同不依赖稀有卡；关键卡改善玩法而非授予整套玩法的存在权。
- 伤害垄断：低投资角色可获得可靠基础成长；辅助行为是否需要合理能量收益需专项验证，避免只按伤害奖励主要输出者。
- 输入过载：技能变多不应让必须手动关注的冷却同步增加。
- 无限触发、伤害膨胀：需要触发来源、内置间隔和递归限制；先用现有节奏验证，避免新增大量对象。
- 控制对 Boss 失效：保留覆盖、削甲、资源和站场输出等替代价值，不承诺所有控制都对 Boss 有效。
- 源码与文案冲突：基础说明中混入旧天赋时需清理，但不是本次直接修改范围。
- 暂停、切场景、存档、倍速、性能：实现后必须验证；本次未作运行结论。
- 资产和授权：仅借鉴规则分工，不复制外部角色、美术或文本。

## 11. 方案比较

| 方案 | 规则 | 收益 | 代价/风险 |
| --- | --- | --- | --- |
| A 保持全部结构，只增加卡牌 | 继续三套角色候选，增加分支/祝福 | 内容增加快 | 可能进一步稀释卡池和增加阅读；不解决分工 |

## 12. 待讨论的设计合同

**决定：pending。以下全部为提案，不是批准的实现规格。**

1. 构筑单位以整队为主。角色分工可以随一局的获得物改变，单个角色没有永久主辅身份。
2. 先测试每角色一个主要需要掌握时机的普通技能；其他技能仍可存在，手动权限保留。该目标衡量认知负担，不等于删除技能或强制只准装备一个技能。
3. 先梳理每个技能的“上场任务、离场留下什么、何时适合切”；需要站场完成的技能明确完成窗口。
4. 基础数值成长能维持全队可用性，关键选择用于改变机制和队伍配合。具体自动成长量待校准，不能直接改坏用户已经确定的基础模板。
5. 三选一作为待试验的展示方案；两张与当前方向相关、一张保留探索的方案同样待试验。用同等总成长预算比较，不能把四选二的收益直接减半。
6. 机制方向能得到推进机会，但不保证每张指定卡必出；提供替代解法。卡牌不再必然按角色占固定席位。
7. 新技能获得、重点培养和已拥有技能进入候选池的关系需要拆清；不把“拿到新技能”变成不可逆的抽牌惩罚。
8. 原型优先沿用当前切换能量，不新增另一条协同能量。检查控制、部署与低伤角色的能量获得是否与队伍分工相容。

时间、概率、互斥、保底、成长量：待原型确定；不得把本文的示意数量当成平衡结论。

反馈合同：先显示角色主要任务及关键技能准备，再显示交接形成的场上条件；不要新增全队十五个必须监控的倒计时。玩家应能在卡片上看见本次变化及适用条件。

生命周期：先使用独立测试场景与配置，正式旧档迁移不适用。任何恢复旧天赋或正式替换升级池均需独立设计记录。

回滚条件：明确分工仍不能降低操作压力；方向发牌导致无脑固定选项；某角色成为无必要的按钮；相同成长预算下玩法更脆弱或更依赖稀有卡。

## 13. 验证计划

### 假设

- H1：明确上场任务且限制必须精确管理的技能数，会减少漏放和无意打断，同时保留切换价值。
- H2：团队基础成长配合方向发牌，会提高构筑完成机会，并减少“拿技能稀释核心”的体验。
- H3：同一短板有多种解法，能让玩家在第二次、第三次尝试中提出并验证不同调整。

### 分阶段试验

1. **交接原型**：固定技能和属性，先不随机成长。只测试能否解释切换原因、完成协同、处理清怪和单体。
2. **成长原型**：保持同一套战斗，比较当前池与定向池；对齐成长预算、敌群、难度与随机种子。
3. **机制原型**：只增加一个跨角色条件或资源转化，避免一次新增整套状态系统。

建议先做 6—10 次有记录的短测，覆盖熟悉项目的用户和不了解内部规则的体验者；这是探索规模，不是统计证明。

观察指标：

- 每次升级的阅读/决定时间、菜单占整局的时间。
- 想推进的方向连续未出现次数、核心配合首次形成时间。
- 玩家能否解释每次切换，是否存在无效切换和频繁看技能栏。
- 三角色的伤害、控制、部署、资源和生存贡献，避免只用伤害占比评价。
- 清怪有效但单体失效的频率，失败后是否能提出可执行调整。
- 在同一方向里是否出现不同可用解法。
- 保持现有画面和攻击表现时的帧时间、对象数及触发数量。

自动检查只验证行为：离场保留/清空、消耗与触发来源、冷却、候选资格、保底与满级边界、暂停和读档；不能证明“好玩”。

图形检查：火路残留和停止新增是否清楚，力场/削甲反馈是否可见，自动与手动是否能理解。键盘操作、文字和颜色辅助信息一起验证。

否定条件沿用第 3、9、12 节；任一核心假设失败应缩小或重做方案。
