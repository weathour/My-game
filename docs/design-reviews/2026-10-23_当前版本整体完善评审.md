## 0. 决策摘要

当前战斗、技能点、20波推进和无尽营地已有可用主体。主要缺口是：玩家长期目标与可交付成果尚未形成故事循环，现有奖励/存档在若干中断路径下不一致，教学与部分信息提示没有跟上当前规则。

建议按“保存与恢复 → 第一条完整故事流程 → 第一章三关 → 教学、反馈与交付验证”实施。当时的详细架构已随新设计清理；实际交付保留在[实施记录](../implementation/2026-10-23_系统框架实施.md)。[旧内容样例](../story/chapter1_framework.example.json)仅作为当时校验的输入保留，不作为新主线内容。

用户已确定：以当前版本为准；本轮不完善人物技能和怪物机制；沿用“前哨清剿 → 裂隙推进 → 星核讨伐”，剧情以后可改，优先健全系统框架。具体命令合同与内容仍是设计建议，状态为 `evidence_ready`，不是 `implemented` 或 `verified`。

完成条件分两层：本轮交付可审查的现状证据、完整状态/数据/交互设计、通过结构检查的样例与实现顺序；后续实装完成须从真实入口跑通三关，并通过中断、迁移、重复提交和模式隔离验收。

## 1. 范围与约束

- 目标玩家：首次进入项目的玩家、已有无尽档的回归玩家；覆盖选档、营地、出击、20波奖励、结算和故事首章。
- 目标体验：知道下一步做什么、为何出击、获得了什么、失败保留什么；三人轮转与构筑仍承担主要操作乐趣。
- 范围内：对话/任务/剧情物品/情报/关卡推进架构，恢复与提交边界，教学、HUD、结果反馈、输入舒适度、性能和交付验证缺口。
- 范围外：技能效果与数值、怪物行为与配置、旧技能树恢复、第五角色、新经济系统、房间分支、自动发布。
- 核心承诺：三角色轮转，各角色可作主力；视觉反馈与手感优先；构筑能改变玩法；小团队可持续迭代。叙事提供行动目的，不把大段必读文本塞进战斗。
- 制作约束：复用现有角色、场景、UI和保存模块；首版不等待新立绘、配音或可走动故事营地。保留旧档与四人roster，在1280×720和960×540检查文字和键鼠可达性。

## 3. 玩家问题与成功标准

当前正式玩家能在无尽营地整备、战斗、加点和领波次祝福，但不能进入完整故事模式。营地介绍和商品服务没有任务的接取、物品交付、情报与后续解锁；死亡页对失败原因和下一次行动帮助有限。

期望玩家从准备页看到当前目标与继续战局，主动确认任务；通关获得明确成果，返营交付后看见下一目的地；忘记台词时可查记录；中断或重复操作不会丢失成果。故事动机、局内构筑和无尽成长各自清楚，不互相覆盖。

成功信号：新玩家能指出下一关和交付对象；关键物品必然可达；三关完成后可回看记录和回刷；同一结果只结算一次；保存失败有可操作的恢复入口。否定条件：看似完成的任务读档后退回、进入无尽导致故事物品丢失、需要读代码才能理解目标、剧情必须靠新技能或新怪物才能推进。

建立任务状态、活动尝试、领取凭据和已知信息；交付撤销对应物品持有，转化为情报与主线进度。重构只触及故事索引推进与保存接线，不重构战斗技能或把各种物品合成统一背包。

核心机制卡——关键物品交付：任务ready、NPC正确、数量足够；玩家确认明确消耗；业务层读取当前档，在一个副本中扣物品、完成任务、解锁下项、记录凭据与对话断点；保存成功后更新界面。失败留在原选项，取消不改状态，重复命令不重扣。

## 5. 链、环、网络与生态

```text
接任务 → 校验当前关卡 → 出击尝试 → 既有胜利事件 → 保存首通与物品
→ 返回NPC → 明示交付成本 → 保存任务/情报/下一目标 → 再出击
```

资源流：关卡固定首通 → 故事物品 → 指定交付 → 永久情报/进度；第三关核心投影到旧 `boss_core_fragments`。关键道具不随机、不占携带容量、不卖不扔；已有无尽骨头、17种携带物和局内装备保持原生命周期。

正反馈来自“行动取得证据、证据开放目标”；有限首通凭据约束重复发奖；失败重试保留故事事实，构成恢复环；任务/物品详情和记录构成学习环。对话、准备页和战斗都是同一个业务入口的调用者，不各自写状态。

上游是现有关卡定义与SaveManager；下游是NPC标记、出击许可、记录和结算反馈。主要竞争资源是玩家注意力与制作成本，故必做交付不在战斗中弹出。敌人组合、角色技能相互作用和新构筑生态本轮不适用；回刷允许试既有阵容，但是否有足够重玩动机仍需玩家测试。

## 9. 退化模式与边界

已确认的主要风险是中断恢复、数据丢失和信息不一致。单一最优策略、主C垄断、敌人反制、技能强度本轮不作结论。没有实测依据宣称高密度必然卡顿，也不把源码复杂等同于玩家帧率问题。

设计边界：可选对话不能锁死任务；主线道具不随机、不卖、不占容量；回刷不重复永久奖；旧档不补扣过去不存在的交付；阵容变化不使NPC消失；重看只显示已见节点且无副作用；开发试玩隔离正式档。若额外章节需要新目标类型，按实际需求扩展，不先建设通用任务编辑器。

输入/舒适度风险需图形验证：当前技能加点“＋”设置 `FOCUS_NONE`；暂停菜单不能直接进入完整改键设置；主设置尚无独立字号、减闪烁/减震动选项。已有响应式字号和设置页焦点修复应保留。资产发布需逐项确认授权，未确认部分不得描述为已可商用。

根因链：成果在界面上出现 → 业务状态与持久状态不同步 → 跨菜单/跨文件恢复丢失必要事实 → 玩家进度或信任受损。故事框架应先建立统一提交与恢复，再增加内容量。

## 11. 方案比较

| 维度 | A 保持现状 | B 最小完整首章（推荐） | C 通用剧情/背包/分支平台 |
| --- | --- | --- | --- |
| 玩家价值 | 无尽可玩，故事仍关闭 | 三关完整目标/成果/记录/回刷 | 可表达更多类型，但首章落地更晚 |
| 核心一致性 | 保留战斗核心，外循环缺口在 | 使用现有战斗承载叙事 | 容易增加与战斗无关的操作 |
| 可读性/决策 | 当前说明债务保留 | 一个必做任务、明确交付、选读 | 需要解释分支、背包、更多资源 |
| 构筑/重玩 | 依赖无尽 | 无尽保持、故事提供练习重访 | 可能更丰富，尚无内容验证 |
| 公平/恢复 | 四项已知缺陷仍在 | 凭据、事务和中断验收明确 | 状态组合更多，恢复成本更高 |
| 制作成本 | 低，但未完成用户目标 | 五个小模块、现有流程接线和一章数据 | 编辑器、泛化目标、经济与迁移成本高 |
| 存档/性能风险 | 既有风险 | 有界schema与少量ID，需迁移测试 | 无界日志/通用库存等更难控 |
| 验证/回滚 | 不解决问题 | 按第一关切片验收；门禁控制开放 | 跨系统回滚和数据兼容复杂 |

只修几条文案或只开放故事按钮无法满足本次需求；完整平台缺少实际内容需求。选B，保留可替换剧情数据与明确扩展点即可。

## 12. 决定与设计合同

以下记录当时确定的规则，后续实际实现见[实施记录](../implementation/2026-10-23_系统框架实施.md)；原架构规格已在2026-10-26清理，不再作为新主线要求：

- 任务五状态；首通与交付分开；下一任务在交付后available，由玩家确认接受。
- 开局明确模式、槽位、stage_id、attempt_id和advance/replay，继续不重新推断关卡。
- 两件关键物品加既有核心字段；来源固定，交付成本固定；无新增随机主线门槛。
- 故事提交先保存待结算运行态，再原子提交永久结果与凭据，成功后清run；重看和重复提交不重发。
- 局内成长每关重置，继续恢复原局；永久进度/核心/情报保留；迁移旧索引不要求补交不存在的物品。
- 台词、名称与人物动机可换；ID变更必须迁移，已完成章节不因内容更新倒退。

反馈合同：接受前说明目标与成果，出击前说明阵容/继续边界，交付前列消耗，成功后展示情报和下一步；保存失败保留操作入口且不伪称成功。战斗命中反馈本轮不适用；UI、音效、标记只表达已提交结果。

回滚条件：出现旧档丢失、重复奖励、主线死路或跨模式污染则保持故事门禁关闭、停用新增入口，保留诊断文件；已升级存档不能直接交给不识别schema的旧版本覆盖。不存在通过删玩家档“回滚”的方案。

## 13. 验证计划

假设：若目标、物品用途和结果持久化都可见，玩家能独立完成三关并理解下一步；若业务写入集中且带凭据，中断和重复动作不会破坏成果。这两条假设仍需真实运行与玩家测试。

本轮已有：15项相关smoke通过；四项缺陷被隔离复现；故事schema丢字段约束确认；首章数据引用/可达性/固定物品预算检查通过。证据见目录。未将拟议新流程当成测试通过。

实装验收：

- [ ] 正式选档→接受→出击→首通→返营→交付→下关→本章完成可达。
- [ ] 每个领奖/交付/过场节点保存退出后正确继续；主档坏而备份好时恢复；双坏时保留原件。
- [ ] 写盘失败、成功后清run失败、双击、旧面板、错槽位/错NPC均不产生半提交或重复奖。
- [ ] 旧索引0/1/2/3、旧活动战局、未知内容版本迁移明确，四人和旧核心余额保留。
- [ ] 故事回刷不推进主线、不再发首通材料；继续保留purpose；无尽档无变化。
- [ ] 键鼠均可操作，改键提示正确，960×540长文本/选择不裁切，焦点与面板控制归还正确。
- [ ] 完整20波至少覆盖一次成功与失败；补N1/N3/N6/N11的代表性档案测量后再讨论调参。
- [ ] 记录构筑、波数/阶段、实体量、p95/p99/max和SavePeak；不能只比平均FPS。

首轮人工测试建议包含首次接触者与已有无尽玩家，分别观察能否指出当前任务、交付人、失败保留项和继续/新开差异；任一人必须靠开发者解释才能通过关键交付，则修正入口与文案后再验，不按“最终通关了”判可读性通过。无须在本轮先建立遥测平台。
