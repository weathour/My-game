# 老版本遗留全局审计与清理方案

2026-10-31｜用户已选择第 3 档清理方向，最终目标是建立并切换到这个游戏专属、全新历史的干净仓库。隔离清理、空目录验收、独立本地仓库及全新克隆检查已完成，实际结果以当前状态为准；本轮没有配置远端或推送。现行规则以[共识](../00_当前设计共识.md)为准，完成状态以[当前状态](../08_当前实现状态与后续重点.md)及源码为准；日期记录保留其发生时的事实。

## 已确认清理目标

让当前文件树成为这个游戏的专属工程，而非同时承载旧幸存者原型与新战役。旧主线、无尽、旧入口、技能／天赋／20 波成长及其专属存档代码、资源、测试、工具和旧指导信息，可随依赖核实完整退出；不再于当前树建立另一套可运行 legacy 或大量旧规格。已提交内容可通过源仓库的 Git 历史追溯；未跟踪的本地文件不属于该历史。

保留判据是当前游戏或明确的开发与生产流程是否需要，而不是“原稿”或“母版”这一名称：仅属于旧游戏且不再使用的制作源也可退出；当前游戏的原画、ASE、显式谱源、运行音频，以及现被复用的人物身体、头像、特效和共享表现层应保留，并切断其对旧玩法逻辑的依赖。当时未跟踪的干分轨、MIDI、RPP 与 FLAC 派生中间文件不随当前仓库保存；两份本地归档已删除，可按保留的谱源、工具和音源清单重新生成，但尚未实际重渲。许可与来源信息继续保留。具体依赖与移除名单须由审计确认，不能只凭目录名判断。

现有 `campaign_v1` 的进度和设置继续可用；不开展旧 story／endless 档向新游戏迁移的兼容开发，也不主动擦除磁盘上的旧档。测试按当前功能与故障边界保留或重建，不以 225 个脚本的数量为目标。独立本地新仓库已在工程收敛和空目录验收之后建立；不重写原仓库历史，也不借清理补新玩法或新美术。

## 执行路线：先收敛，再建立全新历史

建议在现有仓库的独立清理分支或 worktree 中先做依赖切割，再从通过验收的提交导出到空目录，最后在该目录初始化新仓库。直接先建新仓库会把尚未识别的共享依赖和混杂入口一起搬过去；先在原工作区无隔离地大规模删除则难以逐批对照。隔离分支仍可对照现有可运行与 CI 基线，空目录导出则能检验真正需要哪些文件。下面是实施路线；各阶段的实际完成情况以当前状态及最终验收为准。

| 阶段 | 动作与产物 | 进入下一阶段的验收门槛 |
| --- | --- | --- |
| 1. 固定基线 | 从 `f75dfc6` 建立独立清理分支或 [worktree](https://git-scm.com/docs/git-worktree)；冻结 18 战、38 人、剧情、配乐、`campaign_v1`、设置和当前生产素材清单，记录版本、来源与基本验证。 | 基线可运行，现有正式存档和设置有受控副本；清单明确哪些是运行、生产、许可和可再生成证据。 |
| 2. 切分共享依赖 | 按实际调用提取当前游戏所用的身体、头像、特效、设置和音频公共部分，切断通向旧主线／无尽及旧成长的逻辑依赖。已审计的旧入口额外静态可达 333 个 GDScript、63 个场景，只表示可达闭包，不代表它们同时运行；38 人中 22 人使用旧身体作纯表现。另有 7 个孤立脚本约 645 行可单列核验。 | 正式主线在独立环境仍能战斗、显示、出声并保存；逐项验证共享者和真正不再可达者，动态加载的 JSON、资源 UID 以运行与打包证据核对，不能只凭静态搜索删除。 |
| 3. 成组清理旧系统 | 切断入口后，按主场景／player／旧成长／无尽／营地／旧存档等责任组删除专属代码、资源、工具和已退役测试；当前游戏与生产要用的可得原画、谱源及工具保留，纯旧游戏且不再使用的制作源可退出；已删除的未跟踪中间文件按上文边界处理。每组形成变更与替代保护清单。 | 每组先跑对应正式功能、保存、失败回退和资源加载检查；退休的旧合同按实际删除或替换，保留防故障与当前功能保护，不能靠删测试让 CI 变绿。 |
| 4. 收敛信息与完整回归 | 让 README、`00`、`08`、`HANDOFF`、`KNOWN_ISSUES`、`02`、`09` 等只承担当前目标、入口与风险职责；旧规格与旧玩法问题指向来源或历史。迁移所需许可证、来源与生产文档，整理当前适用的测试和 CI。 | 当前功能对应检查、完整适用套件及导出检查通过；核对 18 个战斗节点、38 人及剧情、配乐、设置和存档边界，测试数量不作为目标。 |
| 5. 空目录验收 | 将已提交的清理快照用 [git archive](https://git-scm.com/docs/git-archive) 或可审保留清单导出到全空候选目录；对照清单核验 `export-ignore` 等可能遗漏，保证运行与生产输入完整，不带旧 `.git`、`.godot`、忽略的本地证据、Graphify 缓存或构建物。 | 在候选目录全新导入；以隔离副本验证当前存档与设置读取，并覆盖 18 节点流程、38 人的代表性能力／显示及独立 PCK 加载。记录候选内容、哈希和可重现命令。 |
| 6. 新仓库与 CI | 在通过的候选目录 `git init` 并制作首提交，保留来源许可、旧基线 SHA 和必要生产文档，迁入适用本地检查与素材体积门槛。本轮只创建本地仓库，远端名称、归属和公开性以后再决定。 | 独立全新本地克隆再次导入、运行并通过完整检查；核对首提交、许可、运行资源、动态加载和导出，确认未继承旧库历史。本轮不创建或写入远端。 |
| 7. 切换日常开发 | 新库经验证后，更新日常工作目录、自动化、文档链接与协作入口；旧库停止作为日常开发位置，已提交内容从源仓库历史追溯。 | 团队入口实际指向新库，当前玩家进度及设置可用；相邻本地归档已按用户要求删除，未跟踪内容和原始详细日志不再从该归档取得。 |

Godot 的 [`user://` 路径](https://docs.godotengine.org/en/4.6/tutorials/io/data_paths.html)指向设备上的持久用户数据目录。仓库名称、项目展示名和保存位置不是同一决定：默认保持当前项目保存目录，另行验证平台上的目录解析；不得因顺手改名让现有档案不可见。新库验收先使用隔离副本，保护实际玩家数据。

完成标准是：新库拥有从首提交开始的独立历史，包含当前游戏及明确必要的生产输入和许可；旧玩法入口及其专属系统已退出，当前正式档与设置仍可用；空目录与新库全新克隆验收均通过，日常开发已切换；远端 CI 留待未来另行授权。源码、包和文档的清理范围以逐项清单为准，源仓库已提交历史可供追溯，不宣称旧 Git 历史被缩小。


## 迁移边界

当前游戏的运行资源、动态 JSON、资源 UID、正式存档和设置、许可与必要生产输入均按实际调用保留。测试以功能和故障保护为依据；旧系统测试的数量不作为目标。使用隔离存档副本验证，不主动擦除任何玩家旧数据。
