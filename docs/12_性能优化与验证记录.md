# 性能优化与验证记录

> 2026-10-26整理：本页保留旧版本的工程与测量记录，正文中的“当前”“已定”“后续”指记录时点；不作为新体系要求或当前任务队列。目标以[当前设计共识](00_当前设计共识.md)为准，新设计尚未实施。


本文记录当前密集战斗性能优化的设计边界、已落地改动、已知掉帧原因和 PR 验证方式。目标是在不削弱正式玩法密度、不重写核心战斗、不引入 GDExtension 的前提下，降低主线程帧时间尖峰并保留可复现证据。

## 优化边界

本轮优化遵循以下约束：

- 不通过降低无尽模式敌人数量来掩盖低 FPS。
- 不降低技能、弹幕、掉落物和 Boss 的正式玩法设计目标。
- 不做不可逆的大重写；优先拆分热点路径、批处理、缓存和对象复用。
- 不优先引入 GDExtension；当前仍以 GDScript 和 Godot 场景结构优化为主。
- 所有性能结论优先依赖同场景帧时间、慢帧日志、运行态实体规模和玩法等价 smoke，而不是单次主观体验。

## 已落地优化

### 2026-10-25 生命周期与命中正确性

- 战斗退出显式释放离树敌人/拾取池；延迟伤害 batcher/queue 同时检查目标实例与激活代数，复用不会继承旧命中。死亡、入池和释放的目标也不提前消耗枪手事件。
- 玩家有效投射物取消每步380次跳检，每物理步完成实际路径及到期尾段碰撞。容量1800、MultiMesh与纯视觉弹快路保留。移动目标的“经过后离开”和“后来进入旧路径”均与逐步参考对照；不维护历史敌人位置副本。
- 低帧拥挤不再提前完成出生预警；按帧生成队列保留。
- `performance_counters.gd` 增加队列最老等待、完成最大等待、出队/有效结算/废弃旧代数计数。时间为墙钟微秒，包含暂停；与暂停状态共同解释。
- 保存计时拆成载荷构建、嵌套验证、JSON序列化、主档和备份提交；原总耗时保留。有限标量不再构造诊断路径或递归，运行快照JSON取消对象键排序；验证规则与主备原子写盘保留。
- 专用 `scripts/tests/battle_lifecycle_benchmark.gd` 使用真实主场景、固定负载、真实保存与10次进出；区分墙钟整帧、引擎CPU监控和单次保存/清理时长。它不代替完整20波，也不把局部Boss CPU测试当游戏FPS。

最终测量与回归见[架构整改记录](implementation/2026-10-25_架构健全性整改.md)。

同一3.86MB载荷的完整保存校验中位数由243.2ms降到108.0ms，有限值扫描由187.9ms降到57.2ms；六类INF/NAN的精确报错路径不变。同进程配对的主备写入只减少约4ms，不能把跨进程缓存或CPU频率变化归因于取消排序。敌弹的wave对象缓存实测更慢，已撤回；仅保留同一弹内一次目标准备、跨物理帧刷新和伤害回调后的失效保护。固定步对照的收益小且有波动。

真实主场景最终测量使用i5-14600K / RTX 5080、Godot 4.6.2；X11为Vulkan Mobile与Dummy音频。首轮采样360个process帧，包含约48个敌人和约2000枚敌弹的动态负载。

| 最终首轮整帧墙钟 | Headless | X11 |
| --- | ---: | ---: |
| 平均 | 88.43ms | 83.35ms |
| P95 | 205.94ms | 213.86ms |
| P99 | 442.26ms | 413.22ms |
| 最大 | 458.26ms | 609.71ms |
| 实际物理步数 | 1483 | 1460 |

这仍显著超过16.7ms预算，属于高密度发布风险。相同process帧数不等于相同物理工作量，不能用初次基线与此表计算纯优化带来的FPS提升；初次失败、诊断scope、固定步对照及复现入口完整保留在[性能证据](implementation/evidence/2026-10-25/architecture/runtime/performance-findings.md)。本轮没有减少敌人、跳过有效命中或缩短预警。

两后端各10次进入/退出战斗，等待30个process帧清理后，每轮均为12个节点、0个孤儿节点、738个资源。X11在仅等待2帧时出现740/742个资源，随后回落；初次严格检查失败仍保留。静态内存有小幅变化，不据节点/资源稳定宣称内存完全不增长。

### 2026-09-20 第三轮：玩家弹幕查询、渲染提交与遮挡排序

本轮按“不得降低画面质量或改变角色/怪物技能、攻击方式及相关规则”的约束执行，保留现有分辨率、材质效果、动画帧、描边、特效密度、模拟/绘制频率、弹幕预算、穿透次数、伤害、冷却与敌人数量。

- 单体与批量玩家弹幕共享原空间网格的有序候选数组，缓存按物理帧、网格对象与网格快照版本失效；额外覆盖同帧切场景、原地重建网格和战斗清理。没有缩小查询范围、改变格子顺序或缓存敌人当前位置。
- 批量弹幕先排除已穿透的目标并检查几何相交，仅对相交目标读取生命、复活、回收状态。所有精确判定仍读取当前数据，保持第一个合法命中目标一致；减少大量落空候选上的重复状态读取。
- 批量弹幕的两层 MultiMesh 改为两次整块上传，复用未变化的方向、尺寸和颜色数据，保留每一枚弹幕及描边。互换删除、波形方向变化、原位颜色/尺寸修改、清空和复用都会更新对应实例。普通子弹默认白底过滤材质共享；已指定的独立材质保留。
- 大型怪物遮挡排序原来为每只普通怪反复查询多个 Boss 的阴影位置，现在每次排序只读取一次各 Boss 的位置，计算与“在任意 Boss 后方”完全等价的阈值；不变的 z-index 不重复写入，排序频率不变。

同机 RTX 4070 SUPER、Godot 4.6.2、游戏当前的 Vulkan Mobile 渲染方式；固定 240 只怪物（含 4 只大型怪物）、每种弹幕查询各 240 次、720 枚弹幕渲染提交，预热 3 次、采样 30 次：

| 独立工作量中位耗时 | 第三轮优化前 | 第三轮优化后 | 下降 |
| --- | ---: | ---: | ---: |
| 批量弹幕命中查询 | 111.974 ms | 58.677 ms | 47.6% |
| 单体弹幕候选/几何查询 | 57.149 ms | 51.558 ms | 9.8% |
| 大型怪物遮挡排序 | 3.372 ms | 1.190 ms | 64.7% |
| 720 枚弹幕向渲染器提交 | 1.161 ms | 0.351 ms | 69.8% |

这些是故意堆叠的固定工作量 CPU 计时，不是整局帧时间，也不代表实玩 FPS 同比例提升。优化前后三类目标/排序校验量和显示弹幕数量相同。此查询基准不实际扣血；真实伤害、跨帧穿透、攻击事件和三角色技能由回归测试验证。

新增 `player_projectile_query_smoke.gd` 对照原算法，覆盖候选顺序、负坐标、同帧移动/体型变化、死亡/复活/回收、已命中目标、释放节点、切场景与多 Boss 排序。新增 `player_projectile_render_smoke.gd` 在 Vulkan 与 OpenGL 上将新提交与原逐实例提交逐像素比较，覆盖移动/波形、方向、颜色/透明度、尺寸、描边、互换删除、清空和复用；另核对 1800 枚实例的变换/颜色及自定义材质保留。

本轮 34 项相关逻辑回归通过，两个渲染后端的像素对照通过；headless 启动、文档链接、成就、架构检查和 `git diff --check` 通过，`graphify update .` 已执行。此前已复现的 8 项旧测试失败与配置缺失未计为通过。本轮也重跑了第二轮的纯敌人连续战斗：伤害和位置校验完全相同，平均 18.237 ms、P95 21.873 ms；该场景不含本次优化的玩家弹幕工作量，未出现进一步提速证据。

复现入口 `scripts/tests/combat_query_render_benchmark.gd` 及各次原始 JSON 见 [性能证据](performance/2026-09-20/README.md)。

### 2026-09-20 第二轮：密集避让、敌方弹幕与 Boss 闪光

- 怪物体型半径改为在身体半径、接触半径、参考缩放或实际缩放改变时失效，保留同帧树人成长与节点回收后重新入场的判定。空间网格缓存本帧候选怪物的最大身体半径，先用实时位置与保守距离排除不可能碰撞的目标，再执行原有精确判定；候选顺序、邻居处理上限与推开规则不变。未知体型接口会退回完整精确扫描。
- 敌方弹幕的远近判断使用距离平方，直线弹幕复用未变化的方向角度，生命周期渐隐只在透明度变化时写入。保留 720 / 1900 距离边界、远处更新间隔、运动、命中与回收行为。
- Boss 每个受击叠层只保留一个闪光 Tween，连续命中时重启，避免多个动画同时写同一透明度；无独立参数的白色闪光材质共享。闪光时长、重启亮度和恢复原色均通过测试。

本轮比较基线是**完成第一轮优化的本地工作区**，不是提交 `32b7782`。同机 Godot 4.6.2 headless，沿用 120 只怪物、240 发初始弹幕、每 6 步 60 次命中、预热 30 步后采样 180 步的工作量：

| 逻辑物理步耗时 | 第二轮优化前 | 第二轮优化后 |
| --- | ---: | ---: |
| 平均 | 29.257 ms | 16.721 ms |
| 中位数 | 28.973 ms | 15.945 ms |
| P95 | 33.040 ms | 20.801 ms |
| 最大 | 36.533 ms | 23.650 ms |

平均逻辑步耗时下降约 42.8%。两次测试的 120 只怪物、2100 次玩家命中、12 次敌方弹幕命中、生命总量、玩家受伤量与位置总和完全一致；这组校验只证明该受控场景等价，不代表所有随机实玩轨迹相同，也不能直接换算为实玩 FPS。

240 只密集怪物的避让计算中位数由 62.618 ms 降到 26.148 ms，避让向量校验量一致。512 发直线弹幕的更新中位数由 1.837 ms 到 1.756 ms，但 P95 由 2.214 ms 到 2.437 ms，暂不据此声称弹幕尾部耗时改善。单个 Boss 叠层连续受击 512 次后，待处理 Tween 从 512 个降至 1 个，该刷新工作量由 2.989 ms 到 2.053 ms。

本轮 32 项相关逻辑 smoke 全部通过，覆盖敌人行为、成长体型、弹幕复用与批处理、烈石计时、存档恢复等；新增 Boss 闪光渲染 smoke 在 OpenGL / RTX 4070 SUPER 上通过。密集战斗基准的批处理开关两组玩法计数一致，均有 8 次真实弹幕命中、64 点受伤及 0 次重复 tick。Godot headless 启动、文档链接检查、`git diff --check` 与 `graphify update .` 已执行。第一轮记录的 8 项旧测试失败和 2 项旧配置缺失不在本轮修复范围内。

新增复现入口：`scripts/tests/combat_runtime_optimization_smoke.gd`、`scripts/tests/enemy_boss_flash_render_smoke.gd`、`scripts/tests/projectile_feedback_benchmark.gd`。渲染 smoke 需要图形模式运行；同机对照 JSON 与运行边界见 [性能证据](performance/2026-09-20/README.md)。

### 2026-09-20 密集命中、避让、HUD 与存档

- 直接伤害和排队伤害原来每次命中都会调用 `get_method_list()` 枚举目标全部方法。现在按 Script 与方法名缓存参数范围，仍兼容单参数、带暴击参数及继承接口；切换脚本会使用新的缓存键。
- 空间网格按物理帧、场景、查询格子与格子半径复用只读候选列表，维持候选顺序；精确距离仍按节点当前位置计算。体型半径按模型缩放、参考缩放、身体半径及接触半径失效更新，保留树人成长与模板切换。
- 击杀回能的 HUD 刷新统一使用轻量 payload，维持 30 Hz 限频和即时能量条更新，避免构建完整角色说明。
- 主存档与备份共用一次 JSON 序列化，两个文件仍分别临时写入、flush、原子替换，保存间隔不变。
- 验证过程中补齐烈石独立减甲状态的正常物理更新入口；新测试走真实 `batch_physics_process()`，避免只直接调用计时工具而漏掉运行时入口。

### 运行态注册表与批处理

- 敌人、敌方弹幕、玩家弹幕和掉落物运行态注册改为以实例 ID 字典维护，保留既有 Array 返回 API，减少高密度场景中的重复线性扫描。
- 简单普通敌人支持场景级批量更新，关闭大量普通小怪各自的物理回调调度。
- 敌方弹幕和掉落物支持场景级批量 tick，减少每个节点单独 `_physics_process` 的调度成本。
- 玩家弹幕加入池化复用，回收后会恢复场景自身导出的默认视觉/碰撞参数，避免复用串状态。

### 刷怪尖峰削峰

- 大批量预警刷怪结束时不再把所有新怪集中实例化到同一帧，而是进入待刷怪队列并按帧预算消化。
- 开发者模式可按普通小怪 archetype 批量生成，用于复现密集战斗；开发者批量生成不受普通敌人运行时上限限制。
- 无尽模式不再根据低 FPS 动态降低普通敌人上限，敌人密度继续由刷怪规则、难度 profile 和波次设计决定。

### HUD 与 UI 热点

- 战斗 HUD 的时间、技能冷却、大招能量、小地图等表现刷新目标为 30 FPS。
- per-frame HUD 改用轻量属性 payload，避免每帧构建角色详情、技能进化需求和完整说明文本。
- HUD Label、冷却槽和能量显示会跳过未变化内容，降低 UI 重绘和字符串拼接成本。
- 升级触发后，祝福发牌延后到下一帧，并先暂停战斗；升级/技能奖励确认后，完整 HUD 刷新、战斗存档和连续待处理升级弹窗恢复会延后合并处理，避免点击同一帧堆叠重活。
- 角色面板的三张角色卡、六个技能选择器、普通构筑详情和祝福行采用一次构建、原位更新；技能指向不再整批销毁重建详情节点，也不再给六个选择器重复写入主题 override。当前面板已移除旧三阶段左右树。
- 开发者技能列表会缓存上一份选项内容；列表目前同时包含当前等级天赋与旧 108 节点/路径兼容项。缓存只说明 UI 避免重建，不表示旧节点属于正式玩家流程。
- 1280×720 headless 微基准中的 453ms→18ms、486ms→4ms、445ms→19ms 数据来自旧三阶段面板仍在时的同机前后对比。当前面板已再次变更，这些数字只保留为历史优化证据，不是当前提交的性能保证；需要结论时重新运行同一基准。

### 存档与日志

- 战斗自动存档固定约 2 秒一次，覆盖当前 `run_save.json` 和 `run_save_backup.json`，不会按时间追加历史快照。
- 升级/奖励确认后的补充保存不再立即阻塞点击帧，而是由奖励维护任务延后执行。
- 性能日志开关默认关闭；开启后写入 `user://performance_trace_latest.jsonl`，记录周期样本和慢帧样本。
- 开发者性能面板展示帧时间分位数、SavePeak、实体计数、待刷怪队列、批处理状态和 feature flags。

### 视觉与玩法修复

- 修复“三命诡影”复活过程中目标丢失时卡在地图中央、不可选中且不动的问题。
- 修复“祸月星核”Boss 视觉在重复刷新后被清掉而隐身的问题。
- 批量伤害查询按形状/半径网格边界收集候选，避免一个过大的合并包围盒扫描过多无关目标。

## 之前掉帧的主要原因

这次掉帧不是单一 bug，而是多个主线程热点叠加：

1. **SceneTree 调度压力**：大量敌人、弹幕、掉落物分别跑物理回调，主要卡在 Godot 主线程，不能自然吃满多核，所以会出现 CPU 总占用低但 FPS 低。
2. **线性注册表操作**：运行态对象越多，注册、移除、计数和保存前遍历越容易形成 O(n) 尖峰。
3. **同帧实例化新怪**：大批量怪物同一帧 instantiate、初始化、加入树和设置视觉，会造成新怪出现时瞬间掉到 20 FPS 左右。
4. **HUD 重建过重**：战斗 HUD 曾过于频繁构建完整角色属性、技能需求文本和冷却详情；即使怪不多，长时间游玩也会积累 UI/字符串计算压力。
5. **保存尖峰**：自动保存或奖励后立即保存会遍历敌人、弹幕、经验晶体、回血道具等运行态数组；实体较多时会成为慢帧。
6. **升级/点技能路径堆叠**：升级发牌、应用祝福/技能、完整 HUD 刷新、存档和连续升级弹窗可能挤在确认前后一帧内，造成点击瞬间卡顿。

## 验证方式

每次修改性能相关代码后至少运行：

```bash
./scripts/check_project.sh
/home/weathour/.local/bin/godot-4.6.2 --headless --path . --quit
git diff --check
graphify update .
```

`scripts/check_project.sh` 会自动运行 `scripts/tests/` 下除密集战斗基准外的全部 `*_smoke.gd`，避免新增 smoke 后遗漏接线。`dense_combat_benchmark_smoke.gd` 单独运行，因为它会执行 baseline/candidate 两轮计时并写入结果文件。

其中 `*_render_smoke.gd` 的像素断言使用 OpenGL 真实绘制，其余 smoke 使用 headless。Linux CI 通过 Xvfb 与 Mesa 软件渲染提供虚拟显示；无桌面服务器安装这两项后使用 `xvfb-run --auto-servernum ./scripts/check_project.sh`，不能直接把渲染测试改成 headless，否则会等待不存在的绘制信号。渲染快照写入已忽略的 `.omx/` 或 Godot `user://`。

2026-10-13 在 NVIDIA 与 Mesa llvmpipe 上核验弹丸像素比对：玩家弹丸逐通道最多相差 1/255，Boss 多层透明弹幕最多相差 2/255。测试采用对应的逐通道上限，玩家弹丸仍逐项核对实例数量、变换和颜色；超限直接以非零状态退出。CI 作业另设 20 分钟上限，避免脚本断言中断后无限等待。

当前密集战斗基准除实体数量和重复 tick 外，还会实际触发敌方弹丸命中；evaluator 要求两轮的命中次数、伤害、拾取物总值和实体计数一致，且命中与伤害必须大于零。Headless 结果仍不能替代图形模式长时间游玩和 CPU/core 采样。

手动验证建议：

1. 无尽模式正常游玩，观察升级、技能奖励、小 Boss/Boss 奖励确认前后是否还有瞬间卡顿。
2. 开发者模式使用普通小怪批量生成复现高密度场景，检查新怪入场是否分帧消化。
3. 开启性能日志数秒，复现后关闭，检查慢帧样本中的 `delta_ms`、`save_peak`、`pending_spawns` 和 batch 计数。
4. 对比三名角色中后期技能释放，确认没有因批处理和池化导致伤害、视觉、掉落或碰撞规则改变。

## PR 评审关注点

- 优先看 `scripts/game/*`、`scripts/player/*`、`scripts/ui/hud/*` 和运行态 registry/pool 相关改动。
- 注意本轮优化没有把低 FPS 作为降低正式敌人密度的条件；如果评审发现敌人数量下降，应视为回归。
- 性能日志是临时排查工具，默认关闭，不应改变正式玩法。
- 自动存档仍默认启用，但写入频率固定且覆盖同一运行存档/备份，文件数量不会随时间增长。
