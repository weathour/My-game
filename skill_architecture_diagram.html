技能系统架构总览（数据驱动 + 分层注册）
示意：文件路径均为 scripts/ 下，箭头表示数据/调用流向
① 定义层：每个技能 = 2 个文件
abilities/xxx_ability.gd（外壳）：冷却、触发条件、冷却条文案、存档
player/player_xxx_flow.gd（内核）：伤害倍率、范围、效果结算
统一接口：update / can_trigger / try_trigger / get_cooldown_slot / get_save_data / restore_effect_if_active
② 注册层：技能要“报名”的 2 张表
player_blessing_skill_state.gd：SKILL_ID 常量、ACTIVE_SLOT_SKILL_IDS（有没有冷却槽）、ALWAYS_UNLOCKED（大招默认解锁）、中文名
player_skill_cooldown_flow.gd：ROLE_ACTIVE_SKILL_PROPERTIES（角色 → 技能ID → player 上的实例名）
③ 实例层 + 运行调度层（每帧）
player.gd：每个技能一个实例 var xxx_ability = XXX_ABILITY.new()，外加 _try_trigger_xxx() 包装
player_timer_flow.gd：每帧 ① ability.update（冷却/效果）② 依次自动触发所有 _try_trigger_xxx —— 技能是全自动释放
player_ability_flow.gd：try_trigger_xxx → 检查死亡/升级/锁定 → can_trigger（角色/已解锁/冷却）→ try_trigger
UI：combat_skill_bar.gd 读 get_cooldown_slot 显示冷却条
④ 成长发牌层：技能怎么“获得”
player_build_system.gd：BUILD_DEFINITIONS（解锁卡 unlock_xxx / 强化卡 requires_skill），升级四选二发牌
选解锁卡 → force_unlock_skill 写入解锁状态（blessing_skill_state 的 unlocked / tiers / unlock_order）
选强化卡 → build_levels 计数+1 → 技能内用 get_xxx_bonus 读取加成
⑤ 等级天赋层：3/6/9 级发牌
player_skill_talent_system.gd：LEVEL_TALENT_DEFINITIONS（三个角色的天赋池）→ 3/6/9 级三选一（排除已选/同互斥组/未解锁技能）→ 选择写入 role_special_states 的 level_talents
player_xxx_talent_flow.gd：has_level_talent 判断 → 提供数值加成 → 被伤害结算层（player_damage_resolver / job_queue）消费
⑥ 开发者模式 + 存档
developer_panel / developer_actions.gd：跳过正常发牌直达 —— 强制解锁技能（force_unlock_skill + 清冷却 + 刷新 HUD + 存盘）、直接发天赋、发祝福、发升级
player_run_save_state.gd：保存 blessing_skill_state（解锁）、role_special_states（天赋/强化计数）、ability 自身状态
开发者模式 = 正常流程的“快捷键”，走的是同一套底层写入
核心规律：解锁/天赋/祝福都只是“往状态表里写数据”，效果永远由技能的 flow 在结算时现读。所以加新技能 = 复制一个现成技能模板，改 10 个注册点；加新天赋 = 定义 + 一个消费函数。
